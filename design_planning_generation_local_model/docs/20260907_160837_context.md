识别出用户的关键意图：历史回顾功能**不需要保留完整历史，只需保留每次压缩之后的对话历史**。这意味着修复方向不是"保留完整历史"（方案A过重），而是"让压缩真正生效（删除旧消息）"，同时满足：压缩后 `state.messages` 只保留「摘要 + 最近N条」，历史回顾接口自然只显示压缩后的近期对话。

随后 AI 完成了根因定位与修复：

**根因**: `app/services/agent_engine.py` 的 `_agent_node` 压缩分支返回 `messages + [response]`，但 `messages` 字段用 `add_messages` reducer（追加语义、不替换），导致：
- 压缩时旧消息从不删除，摘要 SystemMessage 每次累积（该线程已出现 5+ 条摘要）；
- `state.messages` 无限膨胀至 `prompt_tokens=262143`（256K 全满），LLM 返回 `finish_reason='length'` 空回复 —— 即线程 `project_1786601717128` "不回复" 的原因；
- 历史回顾接口只显示 Human/AI 消息（跳过 SystemMessage），早期历史被动丢失。

**修复（3 处，仅 `agent_engine.py`）**:
1. 顶部导入 `RemoveMessage`：
   ```python
   from langchain_core.messages.utils import RemoveMessage
   ```
2. `_agent_node` 开头保留压缩前原始列表：
   ```python
   original_messages = list(state.get("messages", []))
   messages = list(original_messages)
   ```
3. 压缩分支改为显式删除被摘要替代的旧消息：
   ```python
   if was_compressed:
       keep_ids = {m.id for m in messages if m.id}
       removals = [RemoveMessage(id=m.id) for m in original_messages if m.id and m.id not in keep_ids]
       return {"messages": removals + messages + [response], ...}
   ```

**验证**: 用独立脚本确认 `langchain_core.messages.utils.RemoveMessage`（langchain_core 1.4.7）+ `add_messages` 删除语义可用（删除 id='1'/'2'，保留 id='3'+新增）；修改后 `ast.parse` 语法检查通过（SYNTAX_OK）、`RemoveMessage` import 通过。

**关键结论**:
- 压缩真正生效后，历史回顾接口无需改动，自动只显示压缩后的近期对话，符合用户需求。
- 卡死的线程 `project_1786601717128` 无需手动清库：修复生效后发一条新消息即触发压缩并恢复。
- 保留了 `maybe_compress_messages` 的 2 元组签名不变，避免破坏 `tests/test_agent.py` 的 3 处调用。
- 附注：`KEEP_RECENT_TURNS=15` 注释写"保留15轮"，实际代码保留 15 条消息（约 7.5 轮），命名与行为不一致，尚未改动（留待用户决定）。
